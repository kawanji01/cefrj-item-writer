## 1. 全体像と用語

### 1.1 検証アーキテクチャにおけるレビュアーの位置

検証はハイブリッド2段構成である（`DECISIONS.md` D-07）。

1. **決定的機械検査**（`machine_check.py`）: 機械化可能な検査を実施する。機械検査の違反は verdict `fail` であり、レビュアーを含む何者も覆すことは**できない**。
2. **独立LLMレビュー**（本文書が定めるレビュアー・サブエージェント）: 機械化不能な判断を担当する。レビュアーは**追加の不合格判定のみ**行うことができ、機械検査の違反を上書きしては**ならない**。

検証項目のどちらが機械でどちらがLLMかの割り当ては `docs/cefrj-validation-spec.md` の検証マトリクスが正である。本文書第3節のチェックリストは、そのうちLLM担当項目の判定手順を定める。

### 1.2 用語

| 用語 | 定義 |
|---|---|
| 候補（candidate） | 生成エージェントが出力した1問分のJSON（`schemas/candidate.schema.json` 準拠） |
| 世代（generation） | 1問に対する生成試行の通し番号。値は `gen1` / `gen2` / `gen3` の3値のみ |
| 判定（verdict） | 機械検査・レビューそれぞれの合否。機械検査違反 = `fail`（覆せない）。レビュー = `pass` / `fail` |
| 世代判定 | ある世代の最終合否。機械検査 `fail` またはレビュー `fail` のいずれかで `fail` |
| 不成立 | 1問が全3世代で合格に至らなかった状態 |
| インフラ障害 | 問題の品質と無関係な実行系の失敗（第6節）。世代を消費しない |
| 入力封筒（envelope） | レビュアー1実行に渡される入力一式（`review_request` JSON＋読み取り許可リソース） |

### 1.3 実行単位

- レビューは**1問1独立レビュー**である。再生成のたびに新しいレビュー実行を起動し**なければならない**（MUST）。
- レビュー実行間で文脈を持ち越しては**ならない**（MUST NOT）。前世代のレビュー結果・候補・生成側の会話履歴は、いかなる形でもレビュアーに渡しては**ならない**（MUST NOT）。
- レビュアーの起動方式はホストツール別に異なる: Claude Code = 専用レビュアー・サブエージェント定義（`.claude/agents/`）をTaskで起動、Codex = `codex exec` 非対話サブプロセス。配線の詳細は `docs/cross-agent-compatibility.md` が正。レビュアーモデルはホストツールのモデル（Claude Code = Claude、Codex = GPT-5.6 sol）とする。
- レビュー1実行あたりの参考目標時間はツール別に `docs/requirements.md` NFR-01a が定める（参考目標であり合否条件ではない）。レビュー1実行に適用するタイムアウトの正は本文書 INF-07 である。

## 2. レビュアー契約

### 2.1 独立性要件

- **RC-01**: レビュアーは生成エージェントと独立したコンテキスト（新規セッション/新規サブプロセス）で実行し**なければならない**（MUST）。
- **RC-02**: レビュアーの入力は、①入力封筒（2.3節）、②読み取り許可リソース（2.4節）の2種に限定し**なければならない**（MUST）。生成側の会話履歴はレビュアーから不可視でなければならない（MUST）。
- **RC-03**: レビュアーは機械検査の違反を「誤検出の疑いがある」と報告**してもよい**（MAY、様式は第7節）が、その場合でも当該違反による `fail` 判定を覆しては**ならない**（MUST NOT）。当該セットでは不合格のままである。
- **RC-04**: レビュアーは追加不合格のみ可である。すなわち、機械検査が検出しなかった違反を新たに `fail` として追加**してもよい**（MAY）が、機械検査の判定を緩和・免除しては**ならない**（MUST NOT）。
- **RC-05**: 同一世代のレビューを複数回実行して結果を選り好みしては**ならない**（MUST NOT）。再実行が許されるのはインフラ障害時のみである（第6節）。

### 2.2 入力封筒（review_request）

入力封筒のJSON構造の正は `schemas/review_request.schema.json` および `docs/json-output-spec.md` である。本節は封筒に**含めなければならない内容**と**含めてはならない内容**を定める。

- **RC-06**: 封筒には次を含め**なければならない**（MUST）:
  1. セット・問題識別情報: `set_id` / `question_id` / 世代（`gen1|gen2|gen3`）/ `format`（形式コード9値のいずれか）/ `level_scale`（`cefr` または `cefrj`）/ 指定レベル。
  2. 対象参照: 語彙問題は語彙エントリID（`lex:<headword>:<pos>`）、文法問題は文法項目ID（`gp:<ID>`）。
  3. レベル上限（オーケストレータが `docs/cefrj-validation-spec.md` の LVL-09〜LVL-11 に従い算出した値）: 例文中の文法構造に許容される導入レベル上限（L_ctx）、および例文語彙に許容されるWordlistレベル上限（帯）。レビュアー自身にこの算出をさせては**ならない**（MUST NOT。算出は決定的処理であり、レビュアーは与えられた上限との比較のみ行う）。
  4. 候補問題JSON全体（`candidate.schema.json` 通過済みのもの）。
  5. 機械検査レポートJSON全体（`machine_report.schema.json` 準拠。verdict が `fail` の場合も含める）。
  6. 制約スナップショット: 当該セットに適用された `data/config/limits.json` の該当値、`data/config/proper_nouns.json` のallowlist全文、教師指定トピック（指定時のみ）。
  7. 読み取り許可リソースのパス一覧（2.4節）。
- **RC-07**: 封筒には次を含めては**ならない**（MUST NOT）:
  1. 生成エージェントの会話履歴・プロンプト・思考過程。
  2. 同一問題の過去世代の候補・機械検査レポート・レビュー結果。
  3. 同一セットの他の問題の内容（対象重複・使い回しの検査はセット横断の決定的スクリプト `set_check.py` の担当であり、レビュアーの担当外である）。
  4. `set.json`（正本）。
- **RC-08**: 封筒は `review_request.schema.json` に対するスキーマ検証を通過してからレビュアーに渡さ**なければならない**（MUST）。不通過はオーケストレータ側の契約違反（`E-CONTRACT-xx`、具体コードは `docs/architecture.md` の目録が正）としてセット中止とする。

### 2.3 レビュアーの参照優先順位

- **RC-09**: レビュアーの判断根拠は次の優先順位に従わ**なければならない**（MUST）: ①正規化データ（`data/normalized/lexicon.json` / `grammar.json`）の原本由来情報 → ②EFL SUMMARY (FULL) 由来の傍証データ（レベル別相対頻度・教科書RANGE） → ③レビュアー自身のCEFR-J準拠の言語知識による推定（推定を用いた場合は必ず `reviewer_estimate` として記録。第3節 CHK-03）。原本根拠のある判断を自身の推定で上書きしては**ならない**（MUST NOT）。

### 2.4 許可される読み取り

- **RC-10**: レビュアーに許可される読み取りは次に限定し**なければならない**（MUST）。いずれも読み取り専用である:
  1. 入力封筒。
  2. `data/normalized/lexicon.json` / `data/normalized/grammar.json` / `data/normalized/meta.json`。
  3. `data/config/limits.json` / `data/config/proper_nouns.json`。
  4. `docs/cefrj-validation-spec.md`（検証規則の参照用）および本文書（チェックリストの参照用）。
  5. `agent/reviewer-core.md`（レビュアー指示書。起動時にプロンプトとして与えられる）。

### 2.5 禁止事項

- **RC-11**: レビュアーは次を行っては**ならない**（MUST NOT）:
  1. ファイルの作成・変更・削除（出力は標準出力またはホストツールの結果返却機構経由のJSONのみ）。
  2. ネットワークアクセス（Web検索・外部API呼び出しを含む）。
  3. RC-10に列挙されていないファイル・ディレクトリの読み取り（特に `output/` 配下、`agent/author-core.md`、リポジトリの他文書）。
  4. 候補問題の修正・書き換え（`suggestion` フィールドでの修正案の**記述**は義務であるが、修正した候補を出力して合格扱いにすることは禁止）。
  5. 教師・作問者との直接対話。
  6. 判定条件の追加・緩和（判定はチェックリストと `docs/cefrj-validation-spec.md` の規則のみに基づく）。

### 2.6 出力（review_result）

- **RC-12**: レビュアーの出力は `review_result` JSON 1個のみでなければならない（MUST）。構造の正は `schemas/review_result.schema.json`。オーケストレータは受領時に必ずスキーマ検証を実施し**なければならない**（MUST）。不通過はインフラ障害として扱う（第6節）。
- **RC-13**: `review_result` に記録し**なければならない**内容（MUST。フィールド名・型の最終形はスキーマが正）:
  1. 識別情報: `set_id` / `question_id` / 世代 / `schema_version`。
  2. `verdict`: `pass` / `fail` の2値。これは**レビュアー担当項目のみ**についての判定である（機械検査違反の写しを理由に `fail` としては**ならない**（MUST NOT）。世代判定の合成はオーケストレータの責務、5.2節）。
  3. チェックリスト実施記録: 第3節の全チェック項目について `check_id`（`CHK-01` 形式）・結果（`pass` / `fail` / `not_applicable`）・所見（日本語1〜3文）。適用外形式の項目は `not_applicable` とする。
  4. 例文文法構造インベントリ: CHK-03 の列挙結果（4.2節）。
  5. `violations[]`: 結果が `fail` の各チェック項目につき1件以上（4.3節）。`verdict` が `fail` のとき1件以上必須、`pass` のとき0件でなければならない（MUST）。
  6. 機械検査誤検出疑い報告: 該当がある場合のみ（第7節）。該当がなければ空配列。
- **RC-14**: `review_result` 内の自由記述（所見・`evidence` の説明部・`suggestion`）は日本語で書か**なければならない**（MUST）。原本・例文からの引用文字列は原文（英語）のまま含めて**よい**（MAY）。

### 2.7 判定の合成

- **RC-15**: レビューは、機械検査の verdict にかかわらず**毎世代実行しなければならない**（MUST）。理由: ①機械検査 `fail` の候補にもLLM担当項目の違反が併存し得るため、再生成への指摘を1回で出揃わせる。②機械検査誤検出疑いの報告機会（第7節）を保証する。この方針は非機能要件の最悪コスト（要求数の6倍の生成＋レビュー、`docs/requirements.md`）と整合する。
- **RC-16**: 世代判定は次の合成規則に従う（MUST）: 機械検査に違反が1件以上ある、**または** `review_result.verdict` が `fail` ならば、その世代は `fail`。両方が違反ゼロ・`pass` のときのみ、その世代は `pass`。

## 3. レビュアーチェックリスト

本節はレビュアーが実施する全チェック項目を、**何を見て・何を根拠に・どう記録するか**の手順書形式で定める。判定手順の正は本節である。各項目の適用形式は本節に明記するが、検証項目×担当×形式の適用表と本節が矛盾した場合は `docs/cefrj-validation-spec.md` の検証マトリクスが正であり、本文書を修正する。

チェックの実施順序は CHK-18 → CHK-01 → CHK-02 → CHK-03 → 以降番号順とし**なければならない**（MUST）。理由: 機械検査レポートの精読（CHK-18）と対象・構造の把握が他の全判定の前提となるため。

形式コードの略記: ①=`vocab_mcq_en2ja` ②=`vocab_mcq_ja2en` ③=`vocab_flashcard_en2ja` ④=`vocab_flashcard_ja2en` ⑤=`grammar_mcq` ⑥=`grammar_cloze` ⑦=`grammar_reorder` ⑧=`grammar_rewrite` ⑨=`grammar_example_selfcheck`。

各項目は次のテンプレートで記述する。

> **見る対象**（候補のどのフィールド・どの文か）／**根拠**（何と照合するか）／**手順**（判定ステップ）／**記録**（`review_result` への記録内容）

### CHK-01 対象文法構造の実現（適用: ⑤⑥⑦⑧⑨）

- **見る対象**: 例文（⑧は目標文）。⑥は加えて空欄位置。
- **根拠**: `data/normalized/grammar.json` の対象項目（封筒の `gp:<ID>`）のパターン略記・Grammatical Item・Sentence Type（文タイプ）。
- **手順**:
  1. 対象項目のパターン略記を読み、例文中でそのパターンに一致する語列（スパン）を特定する。TreeTagger正規表現による機械照合はv2課題（`docs/requirements.md` のスコープ外リスト参照）であり、本チェックはパターン略記を根拠とするLLM照合である。
  2. 一致スパンが存在しない場合は `fail`。
  3. 対象項目に文タイプ指定がある場合（空欄でない場合）、例文の文タイプ（肯定/否定/疑問/命令の別）が一致することを確認する。不一致は `fail`。
  4. ⑥のみ: 空欄が手順1で特定したスパンの内部（対象構造の実現部分）にあることを確認する。空欄が対象構造と無関係な位置にある場合は `fail`。
  5. ⑧のみ: 手順1〜3を目標文に適用する。加えて元文→目標文の書き換え操作が対象項目の文法操作に対応していることを確認する。対応しない場合は `fail`。
- **記録**: チェック結果に一致スパン（例文中の語列を引用）を所見として記録する。`fail` 時は violations に `code: "CHK-01"`、`location` に例文（または目標文）、`evidence` に対象項目の `gp:<ID>`・文法項目名・パターン略記の引用を記録する。

### CHK-02 対象語の用法・語義（適用: ①②③④）

- **見る対象**: 例文中の対象語の出現箇所（レンマ一致の出現位置と回数は機械検査レポートに記載済み）、①②では正解選択肢の日本語語義、③④では対訳中の対象語の訳。
- **根拠**: `data/normalized/lexicon.json` の対象エントリ（`lex:<headword>:<pos>`）の headword / pos / CEFRレベル、および `docs/question-generation-spec.md` の日本語語義規則（辞書形式・品詞反映・指定レベルでの代表語義）。
- **手順**:
  1. 例文中の対象語の用法の品詞が、対象エントリの pos と一致することを確認する（例: `lex:watch:verb` が対象なのに例文で名詞 watch として使われていれば `fail`）。
  2. 例文中の対象語の語義が、指定レベルでの代表語義であることを判断する。同一 headword+pos でも明白に高度・周辺的な語義での使用は `fail`（`expected_level` にはレビュアーが妥当と考えるレベルを `reviewer_estimate` 根拠で記す）。
  3. ①②のみ: 正解選択肢の語義が、例文中の用法と同じ語義を表していることを確認する。例文の用法と語義選択肢が食い違う場合は `fail`。
  4. ③④のみ: 対訳中で対象語に対応する訳語が、対象語の代表語義を反映していることを確認する。
- **記録**: 所見に「用法の品詞・語義の判定」を1文で記す。`fail` 時は `code: "CHK-02"`、`location` に該当箇所、`evidence` に `lex:` ID と原本レベルの引用。

### CHK-03 例文中の全文法構造の列挙とレベル判定（適用: 全9形式）

本項目はゴールデンケース（A1の these を学ぶ問題の例文にA2相当の関係節が含まれる → 不合格）を検出する中核チェックである。

- **見る対象**: 例文の全文（2文構成の場合は両文。⑧は元文と目標文の両方。①②の選択肢文言は対象外、⑤の選択肢は CHK-07 で扱う）。
- **根拠**: `data/normalized/grammar.json`（教員版レベルが正）、傍証として同梱されるEFL SUMMARY (FULL) のレベル別相対頻度・教科書RANGE、封筒で与えられた文法構造の導入レベル上限（L_ctx）。`level_source` の付与規則の正は `docs/cefrj-validation-spec.md` の LS-01〜LS-05、レベル比較規則の正は同文書の LVL-08。
- **手順**:
  1. 例文に含まれる文法構造を**すべて**列挙する。列挙単位は教員版の文法項目粒度とする。教員版256項目のいずれにも該当しない構造（未付与16項目の構造を含む）も列挙から除外しては**ならない**（MUST NOT）。
  2. 列挙した各構造に `level_source` を必ず付与する（MUST。規則の正は LS-01〜LS-03）:
     - `kyoinban`: `grammar.json` にレベル付きエントリ（`level.source` が `kyoinban_direct` または `kyoinban_inherited`、すなわち教員版直接付与または枝番の親レベル継承）がある場合。`gp:<ID>` とレベル値（`kyoinban.level_raw`、単一値または範囲値のまま。継承の場合は親の `gp:<ID>` と継承の旨を併記）をそのまま引用する。
     - `reviewer_estimate`: レベル付きエントリがない場合（未付与16項目とその枝番、および原本のいずれにも該当項目がない構造）。CEFR-J準拠の推定導入レベル（`A1.1`〜`B2.2` の9値のいずれか）と、推定根拠の記述（言語学的根拠、および傍証データに手掛かりがあればその引用）を付す。
     - `kyoinban` にできる構造を `reviewer_estimate` で処理しては**ならない**（MUST NOT）。
  3. 各構造の**導入レベル**（`kyoinban` 範囲値は下限、単一値はその値、`reviewer_estimate` は推定値）を、封筒のレベル上限（L_ctx）と比較する（LVL-08。`level_max` を文脈判定に使っては**ならない**（MUST NOT））。導入レベルが上限を超える構造が1つでもあれば `fail`。
  4. ⑧のみ: 手順1〜3を元文・目標文の双方に適用する。どちらか一方でも超過があれば `fail`。
- **記録**: 列挙結果全体を例文文法構造インベントリとして `review_result` に記録する（4.2節。合格時も必ず記録する（MUST）。原本根拠の判定と推定の判定が常に区別可能であることの受け入れ検証に用いる）。`fail` 時は超過構造ごとに violations 1件: `code: "CHK-03"`、`location` に該当スパン、`evidence` に `level_source` 別の根拠、`expected_level` に上限、`actual_level` に当該構造の導入レベル、`suggestion` に上限内の構造への書き換え案。

### CHK-04 例文語彙の用法レベル（適用: 全9形式）

機械検査はレンマのリスト所属・レベル・免除（数字・記号・句読点・縮約展開・固有名詞allowlist）を照合済みである。本項目はトークン照合では検出できない残余を扱う。

- **見る対象**: 例文（⑧は元文・目標文の両方）中の、対象語以外の全語および語連鎖。
- **根拠**: `data/normalized/lexicon.json`（複数語見出しを含む）、機械検査レポートのトークン照合結果、封筒の語彙レベル上限。
- **手順**:
  1. 個々のトークンはリスト内でも、連鎖としては上限超の複数語表現・イディオム・句動詞として機能している箇所がないか例文を通読する（例: 個々の語がA1でも、イディオム的意味が例文理解に必須ならその表現の難度で判定する）。lexicon.json に複数語見出しとして収録されている表現はそのレベルを根拠とし（`evidence` は `lex:` ID）、収録されていない表現は `reviewer_estimate` 相当として推定レベルと根拠を記す。
  2. 多義語が上限レベル超の語義で使われている箇所がないか確認する（判定基準は CHK-02 手順2と同じ。ただし対象語以外の全語に適用）。
  3. 上限超の用法が例文の理解・解答に必須である場合は `fail`。
- **記録**: `fail` 時は `code: "CHK-04"`、`location` に該当表現、`evidence` に `lex:` ID または推定根拠、`expected_level` / `actual_level` を記入。

### CHK-05 正解の一意性（適用: ①②⑤⑥⑧。⑦の一意性は CHK-14 が担当し、⑦では本項目を `not_applicable` とする）

- **見る対象**: ①②⑤は全選択肢と例文・設問。⑥は空欄・正答・正答同値表記リスト。⑧は目標文の空欄と正答。
- **根拠**: レビュアーの言語判断（一意性は原本参照では判定できないため。所見に理由を必ず記す）。
- **手順**:
  1. ①②: 誤答選択肢のいずれかが、例文中の対象語の語義として成立し得るなら `fail`。
  2. ⑤: 誤答選択肢のいずれかを空欄に入れても文法的かつ意味的に成立するなら `fail`（誤答の「不成立が必須」要件の裏面。表面は CHK-07）。
  3. ⑥: 空欄に、正答とその同値表記リストのいずれにも含まれない語句を入れても、文全体が文法的かつ意味的に正しく、対象文法構造の実現として成立する解答が存在するなら `fail`（同一解答の表記変種の漏れは CHK-15 の担当。本手順は異なる語句による別解を扱う）。
  4. ⑧: 目標文の空欄に、正答（同値表記を含む）以外の語句を入れても指示どおりの正しい書き換えとして成立するなら `fail`。
- **記録**: `fail` 時は `code: "CHK-05"`、`location` に成立してしまう選択肢/語句、`evidence` に成立する読みの説明、`suggestion` に選択肢または文の修正案。

### CHK-06 語彙誤答の適格性（適用: ①②）

誤答の由来（headword+pos+level）の実在・同レベル・同品詞（または記録済み緩和）の照合は機械検査の担当である。本項目は意味的判断を担当する。

- **見る対象**: 3つの誤答選択肢（①は日本語語義、②は英単語）と、正解・対象語。
- **根拠**: `data/normalized/lexicon.json` の各誤答由来エントリと同レベル・同品詞の生候補、機械検査レポートの誤答照合結果。
- **手順**:
  1. 各誤答が正解の同義語・区別不能語でないことを確認する。学習者が正解と区別できない誤答は `fail`。
  2. ①のみ: 誤答の日本語語義が、**正解語（対象語）の別義**と重なっていないことを確認する。重なる場合は `fail`（例: 対象語に2つの語義があり、誤答文言がその第2義に一致してしまう場合）。
  3. ②のみ: 誤答の英単語が、設問の日本語語義の訳として成立しないことを確認する。成立する場合は `fail`（CHK-05手順1と同根だが、こちらは誤答語の語義側から確認する）。
  4. 誤答の排除（正解の特定）に指定レベル超の語彙知識が不要であることを確認する。必要なら `fail`。
  5. `body.pos_pool_relaxed = true` の場合、対象自身を除く同レベル・同品詞の生候補を確認し、GEN-13の3により正解語の同義語・正解語と意味の区別が不能な語を除外する。例えば対象 `do` に対する `does`、対象 `have` に対する `has` は生候補には含めるが、正解と区別不能なので有効候補から除外する。除外後の有効候補が3語以上なら、緩和は不要なので `fail`。3語未満なら緩和の必要性を確認できる。生候補数だけで判定してはならない。互換品詞群と異品詞誤答の実使用は機械検査が担当する。
- **記録**: `fail` 時は `code: "CHK-06"`、`location` に該当誤答または `body.pos_pool_relaxed`、`evidence` に誤答由来の `lex:` ID と重なる語義の説明、または緩和不要と判断した有効な同品詞候補3件の `lex:` ID を記録する。

### CHK-07 文法誤答の適格性（適用: ⑤）

- **見る対象**: 3つの誤答選択肢と空欄・例文。
- **根拠**: `data/normalized/grammar.json` の対象項目、封筒のレベル上限。
- **手順**:
  1. 各誤答が対象項目と同一パラダイム内の操作（同じ文法カテゴリ内の別形・別選択）であることを確認する。無関係なカテゴリの語句は `fail`。
  2. 各誤答を空欄に入れると文法的または意味的に不成立となることを確認する（不成立でなければ CHK-05 手順2で `fail` になっているはずである。両観点で確認する）。
  3. **誤答の排除に指定レベル超の文法知識を要求しないこと**を確認する: 各誤答について「この誤答が誤りだと分かるために必要な知識」を特定し、その知識の導入レベルが封筒の上限内であることを判断する。上限超の知識が必要なら `fail`。
- **記録**: 所見に手順3の判断（誤答ごとの排除根拠となる知識とそのレベル）を要約する。`fail` 時は `code: "CHK-07"`、`location` に該当誤答、`evidence` に必要知識とそのレベル根拠（`kyoinban` 引用または推定根拠）。

### CHK-08 日本語語義・訳の質（適用: 全9形式）

- **見る対象**: ①②の語義選択肢の文言、③④の対訳、⑤〜⑨の例文訳、⑧は元文・目標文の訳。
- **根拠**: `docs/question-generation-spec.md` の日本語規則（Q13）: 語義は辞書形式・品詞反映（「〜を放棄する」「異常な」）、訳はです・ます調基本の自然かつ忠実な訳（会話文は発話として自然な文体可）。
- **手順**:
  1. 語義文言が辞書形式かつ品詞を反映していることを確認する（動詞なら「〜を/〜が…する」形、形容詞なら終止形）。
  2. 訳が原文に忠実であること（脱落・付加・誤訳がないこと）を確認する。
  3. 訳がです・ます調（会話文は自然な発話文体可）で、日本語として自然であることを確認する。
  4. いずれかを満たさなければ `fail`。
- **記録**: `fail` 時は `code: "CHK-08"`、`location` に該当文言、`evidence` に規則との差異の説明、`suggestion` に修正訳。

### CHK-09 訳文からの英文復元可能性（適用: ④）

- **見る対象**: 表面の日本語訳と裏面の英文。
- **根拠**: `docs/question-generation-spec.md` の形式④規則（時制・数・人称の反映）。
- **手順**:
  1. 日本語訳だけを読んで英文を復元する場合に、時制・数（単複）・人称が訳文から一意に決まるかを確認する。
  2. 訳文が複数の英文（時制違い・単複違い・人称違い）に等しく対応してしまう場合は `fail`。
- **記録**: `fail` 時は `code: "CHK-09"`、`location` に訳文、`evidence` に復元不能な情報（時制/数/人称のどれか）と両解釈の例、`suggestion` に情報を反映した修正訳。

### CHK-10 解説の内容・文体（適用: ⑤⑥⑦⑧⑨）

字数上限（⑨=400字、⑤⑥⑦⑧=200字）の計測は機械検査の担当である。本項目は内容と文体を担当する。

- **見る対象**: 候補の解説フィールド全文。
- **根拠**: `docs/question-generation-spec.md` の解説規則（Q13/Q24）、`data/normalized/grammar.json` の対象項目の文法項目名。
- **手順**:
  1. 内容要件を形式別に確認する。欠落があれば `fail`:
     - ⑤: 正解の理由＋**各**誤答の排除理由（3誤答すべて）。
     - ⑥: 正解形が要求される文法的理由。
     - ⑦: その語順になる根拠。
     - ⑧: 元文と目標文の文法的関係。
     - ⑨: ①項目の機能 → ②この例文での使われ方 → ③注意点・よくある誤り、の3部構成。
  2. 教員版の文法項目名（教師向け表示名=「文法項目(平易版)」）が解説中に明記されていることを確認する。なければ `fail`。
  3. 文体を確認する: です・ます調、読者は指定レベルの学習者、文法用語は中学・高校の標準的用語のみ（言語学の専門用語は `fail`）。
  4. 解説の記述内容が文法的に正確であることを確認する。誤った説明は `fail`。
- **記録**: `fail` 時は `code: "CHK-10"`、`location` に該当箇所、`evidence` に欠落要件または誤り内容、`suggestion` に修正文案。

### CHK-11 英文の自然さ（適用: 全9形式）

- **見る対象**: 例文（⑧は元文・目標文の両方、⑤は正解を空欄に入れた完成文）。
- **根拠**: レビュアーの英語話者的言語判断（所見に理由必須）。
- **手順**:
  1. 文法的誤り（一致・語順・冠詞・前置詞の誤用）がないことを確認する。
  2. 語法・コロケーションが自然であることを確認する（文法的には正しいが母語話者が言わない表現は `fail`）。
  3. 文が意味的に成立し、脈絡なく不可解でないことを確認する。
- **記録**: `fail` 時は `code: "CHK-11"`、`location` に該当表現、`evidence` に不自然さの説明、`suggestion` に自然な代替表現（代替表現もレベル上限内でなければならない）。

### CHK-12 学習上の適切さ（適用: 全9形式）

- **見る対象**: 候補の全テキスト（例文・訳・選択肢・解説）。
- **根拠**: 固有名詞allowlistの選定基準（学習者に馴染み・文化的中立。正は `docs/cefrj-validation-spec.md` MC-18 の免除規則）に準じた内容基準、およびレベル帯内の難度判断（D-08: 帯単位判定（`docs/cefrj-validation-spec.md` LVL-09〜LVL-11）の限界はLLMの学習適切性判断が補完する）。
- **手順**:
  1. 暴力・差別・性的内容・政治宗教的争点・特定個人や集団を貶める内容・危険行為の推奨が含まれないことを確認する。含まれれば `fail`。
  2. 教室での使用に不適切な話題（学習者の年齢層に不適合な話題）がないことを確認する。
  3. 帯内難度の補完判断: 機械検査を通過していても、例文が同一レベル帯内で著しく難度の高い語の組合せに偏り、指定レベルの学習者に実用上読めないと判断される場合は `fail`（所見に具体語を挙げること）。
- **記録**: `fail` 時は `code: "CHK-12"`、`location` に該当箇所、`evidence` に不適切性の説明。

### CHK-13 指定レベル超の前提知識（適用: 全9形式）

CHK-03（文法構造）・CHK-04（語彙用法）・CHK-07（誤答排除知識）でレベル超が個別に検出される。本項目はそれらに分類されない残余の前提知識を扱う総括チェックである。

- **見る対象**: 「この問題に正答するために学習者が知っていなければならないことすべて」。
- **根拠**: 封筒のレベル上限、傍証データ、レビュアーの推定（根拠記述必須）。
- **手順**:
  1. 正答への到達過程を学習者の視点で再構成し、必要な知識を列挙する。
  2. 次の種類の知識について、指定レベル超のものが必須になっていないか確認する: 語用知識（皮肉・婉曲・慣用的応答）、文化的背景知識（特定文化の制度・習慣の理解が前提となるもの）、教科知識（数学・理科の専門的内容）、正書法・句読法の高度な規則。
  3. 該当があれば `fail`。
- **記録**: `fail` 時は `code: "CHK-13"`、`location` に該当箇所、`evidence` に必要となる知識の内容と、それがレベル超であることの根拠（`reviewer_estimate` 相当の推定根拠記述）。

### CHK-14 整序の別解非存在（適用: ⑦）

シャッフル結果が正解順と同一でないことの検査は機械検査の担当である。

- **見る対象**: 提示トークン列（シャッフル済み・小文字化済み）と正解順。
- **根拠**: レビュアーの言語判断（所見に検討した並びを記す）。
- **手順**:
  1. 提示トークン全部をちょうど1回ずつ使って作れる、正解順以外の文法的に正しく意味の通る並びが存在しないかを系統的に検討する（主語と目的語の入れ替え、副詞句の位置移動、等価な語順変種を必ず検討する）。
  2. 別解となる正しい並びが1つでも存在すれば `fail`。
- **記録**: 所見に検討した代表的な並びと棄却理由を記す。`fail` 時は `code: "CHK-14"`、`location` に別解の並び全文、`evidence` にそれが正しい文である説明、`suggestion` にトークン構成の変更案（別解を潰す語の追加・変更）。

### CHK-15 穴埋めの同値表記リスト（適用: ⑥）

- **見る対象**: 空欄の正答と、候補JSONの正答同値表記リスト。
- **根拠**: `docs/question-generation-spec.md` の形式⑥規則（縮約形の同値扱い）。
- **手順**:
  1. **網羅**: 正答と同値の妥当な表記（縮約形と非縮約形の対、大文字小文字以外の正書法変種）がリストから漏れていないか確認する。漏れがあれば `fail`（正しい解答が不正解判定される欠陥）。
  2. **過剰**: リスト内に、文法的に誤った形・意味の変わる形が含まれていないか確認する。含まれていれば `fail`（誤答が正解判定される欠陥）。
  3. リスト内の全表記が指定レベル制約を満たすことを確認する。
- **記録**: `fail` 時は `code: "CHK-15"`、`location` に漏れた/過剰な表記、`evidence` に同値性（または非同値性）の説明、`suggestion` にリスト修正案。

### CHK-16 書き換えの指示と両文の適格性（適用: ⑧）

- **見る対象**: 問題文（書き換え指示）・元文・目標文。
- **根拠**: `docs/question-generation-spec.md` の形式⑧規則。
- **手順**:
  1. 問題文に「何を使って書き換えるか」の指示が明示されていることを確認する。指示がない・曖昧な場合は `fail`。
  2. 指示どおりに書き換えると目標文が一意に得られることを確認する（CHK-05手順3と併せて確認）。
  3. 元文・目標文の**双方**が指定レベル制約を満たすことを確認する（文法構造は CHK-03 手順4、語彙は CHK-04 で両文に適用済みであることを照合する）。
  4. 目標文の空欄方式が、書き換えの核心部分（対象文法操作の実現部分）を空欄にしていることを確認する。無関係な部分の空欄は `fail`。
- **記録**: `fail` 時は `code: "CHK-16"`、`location` に該当箇所、`evidence` に規則との差異。

### CHK-17 2文例文の正当性（適用: ⑤⑥⑦⑧⑨。例文が2文の場合のみ、それ以外は `not_applicable`）

- **見る対象**: 2文構成の例文と、候補JSONに記録された要求元文タイプ。
- **根拠**: `data/normalized/grammar.json` の対象項目の Sentence Type（文タイプ）。例文が原則1文であることと要求元文タイプの記録有無の検査は機械検査・スキーマの担当である。
- **手順**:
  1. 候補JSONに記録された要求元文タイプが、対象項目の文タイプと一致することを確認する。
  2. その文タイプが実際に先行文脈を要求するもの（応答文・照応を含む文タイプ）であることを判断する。先行文脈なしで自然に成立する文タイプなのに2文になっている場合は `fail`。
  3. 第1文が、第2文（対象構造を含む文）の先行文脈として自然に機能していることを確認する。
- **記録**: `fail` 時は `code: "CHK-17"`、`location` に第1文、`evidence` に文タイプの引用と判断理由。

### CHK-18 機械検査レポートの精査（適用: 全9形式）

- **見る対象**: 封筒内の機械検査レポート全体（違反一覧 `violations[]`・警告 `warnings[]`（`W-POS-01` / `W-PROPN-01` / `W-LEMMA-01`、`docs/cefrj-validation-spec.md` の MC-29）・計測値 `stats`: 語数・対象語出現回数・トークン照合結果・字数）。
- **根拠**: レポート自体と、`data/normalized/lexicon.json` / `grammar.json` の該当エントリ。
- **手順**:
  1. レポートの全違反を読み、各違反の指摘箇所を候補と突き合わせる。
  2. 違反のうち、機械検査の誤検出（レンマ化誤り・品詞タグ付け誤り・複数語見出しの照合漏れ・免除規則の適用漏れ）が疑われるものを特定する。警告（`warnings[]`）は誤検出調査の手がかりとして用いる（MC-03）。疑いの判定基準と報告様式は第7節。
  3. レポートの計測値（語数・出現回数）を自身の判定（CHK-02・CHK-04）の入力として利用する。計測値そのものを再計算・上書きしては**ならない**（MUST NOT）。
- **記録**: 誤検出疑いがあれば第7節の様式で `review_result` に記録する。疑いがなくても本チェックの実施記録（`pass`＝精査済み・疑いなし）を残す。本チェックの `fail` は存在しない（結果は `pass` または `not_applicable` のみ。誤検出疑いは violation ではなく第7節の報告として記録する）。

### CHK-19 トピック整合（適用: 全9形式。教師がトピックを指定した場合のみ、それ以外は `not_applicable`）

- **見る対象**: 例文（および③④の対訳）。
- **根拠**: 封筒の制約スナップショット内の教師指定トピック。
- **手順**:
  1. 例文の題材が指定トピックに沿っていることを確認する。無関係な題材は `fail`。
- **記録**: `fail` 時は `code: "CHK-19"`、`location` に例文、`evidence` に指定トピックと実際の題材の対比。

## 4. 記録様式（review_result の内容要件）

構造・型・必須性の正は `schemas/review_result.schema.json`。本節は各記録の**記入規則**を定める。

### 4.1 チェックリスト実施記録

- **RR-01**: CHK-01〜CHK-19 の全項目について実施記録を残さ**なければならない**（MUST）。省略・欠番があってはならない。適用外の項目は `not_applicable` とし、所見にその理由（形式不一致/条件不成立: 「形式③のため」「例文が1文のため」「トピック指定なしのため」のいずれか）を記す。

### 4.2 例文文法構造インベントリ

- **RR-02**: CHK-03 の列挙結果を、構造ごとに次の内容で記録し**なければならない**（MUST）:
  - 構造の名称（`kyoinban` の場合は教員版の文法項目名をそのまま使用）
  - 例文中の該当スパン（語列の引用）
  - `level_source`: `kyoinban` または `reviewer_estimate` の2値のみ
  - `kyoinban` の場合: `gp:<ID>` と教員版レベル値（範囲値は範囲のまま引用）
  - `reviewer_estimate` の場合: 推定導入レベル（9段階の1値）と根拠記述（日本語。傍証データを使った場合はその数値を引用）
- **RR-03**: 合格・不合格を問わずインベントリを記録し**なければならない**（MUST）。原本根拠の判定と推定の判定は、`level_source` の値によって常に機械的に区別可能でなければならない（MUST。受け入れ基準に対応: `docs/testing-and-acceptance.md`）。

### 4.3 violations[] の記入規則

- **RR-04**: `violations[]` の各要素は次のフィールドを持つ（構造の正はスキーマ）: `code` / `location` / `evidence` / `expected_level` / `actual_level` / `suggestion`。記入規則:
  - `code`: 違反を検出したチェック項目のID（`CHK-01`〜`CHK-17`、`CHK-19`。`CHK-18` は violation を生成しない）。本文書のチェックIDが違反コードの正である。機械検査の違反コード体系は `docs/cefrj-validation-spec.md` が正であり、レビュアーが機械検査コードを `violations[]` に使っては**ならない**（MUST NOT）。
  - `location`: 候補内の違反箇所。該当フィールド名と、テキスト内の該当語列の引用を併記する。
  - `evidence`: 根拠。原本参照（`lex:<headword>:<pos>` / `gp:<ID>` とレベル値の引用）または推定根拠（`reviewer_estimate` 相当の記述）。どちらであるかが読み取れる書き方をし**なければならない**（MUST）。
  - `expected_level` / `actual_level`: レベル系違反（CHK-02, 03, 04, 07, 13 のレベル超過）では必須記入。レベルと無関係な違反（CHK-05, 08, 09, 10, 11, 12, 14, 15, 16, 17, 19）では null とする（null の可否の最終形はスキーマが正）。
  - `suggestion`: 再生成側がそのまま採用できる具体的な修正案（修正後の文・選択肢・訳・解説の文案）。「修正してください」のような行為指示のみの記述をしては**ならない**（MUST NOT）。
- **RR-05**: 1つのチェック項目で複数の独立な違反を検出した場合、violation を違反箇所ごとに分けて記録し**なければならない**（MUST）（例: CHK-03 で超過構造が2つ → violations 2件）。

## 5. 再生成ループ仕様

### 5.1 パラメータと前提

- **RG-01**: 1問の世代上限は3（初回 `gen1` ＋再生成 `gen2` / `gen3`）とする。この値は `data/config/limits.json` の運用パラメータであり、既定値3。本節の遷移は世代上限3を前提に記述するが、実装は `limits.json` の値を読ま**なければならない**（MUST）。
- **RG-02**: セット内の問題は `q01` から順に**逐次**処理し**なければならない**（MUST）。並行生成をしては**ならない**（MUST NOT）。理由: セット横断検査（`set_check.py`）を確定済み問題に対する増分検査として決定的に実施するため。
- **RG-03**: セット試行対象総数（初期対象＋補充・代替対象の延べ数）は要求問題数Nの2倍を超えては**ならない**（MUST NOT）。

### 5.2 問題ループの状態遷移表

| T1 | 生成(g) | 生成エージェントが候補を出力し、candidate受理検証（生出力のUTF-8・標準JSON、`validate.py`のcandidateスキーマ、厳格パース、JS-01正準化）を全て通過 | 機械検査(g) | `<qid>.<g>.candidate.json` |

| T3 | 生成(g)・再指示後 | candidate受理検証不通過（同一世代内2回目） | 世代消費: g<`gen3` なら 生成(g+1)、g=`gen3` なら **不成立** | `<qid>.<g>.candidate.invalid2.txt` |

- **RG-04**: 世代が消費されるのは T3（candidate受理検証2連続不通過）・T8（世代判定 `fail`）・T11（セット横断違反）の3遷移のみである。T6（インフラ障害）は世代を消費しては**ならない**（MUST NOT）。
- **RG-05**: T2 の再指示では、生成エージェントにcandidate受理検証の診断（`validate.py`のstdout、stdoutがない場合はstderr、厳格パース・正準化失敗では失敗段階・例外型・理由・取得可能な位置）を渡して同一世代内での再出力を求める。再指示が成功した場合（T1）、その候補が当該世代の候補となる。

### 5.3 セットループの状態遷移表

- **RG-06**: 確定問題数が0のまま全スロットの処理が終わった場合、確定処理へ進んでは**ならない**（MUST NOT）。教師照会でセット中止のみを提示する（減数の結果0問となる選択は認めない）。
- **RG-07**: `set.json` はセット完成時（S9）のみ書き込む（原子的完成、D-20）。中止（S7/S8/S10）では `set.json` を書かず、`output/<set_id>/review/` の監査のみが残る（未完成であることが `set.json` の不存在から自明になる）。
- **RG-08**: 減数（S6）で確定した場合、実際の問題数が要求数を下回った事実と各スロットの帰結を監査に記録し、完了報告（`docs/interaction-flow.md` の完了報告様式）で教師に明示し**なければならない**（MUST）。オーケストレータは確定処理（S9）で `finalize_set.py` に渡すセットメタデータの `final_question_ids`（`docs/json-output-spec.md` FIN-01）に、確定した問題の `question_id` のみを列挙し、減数・不成立スロットのIDを含めては**ならない**（MUST NOT）。

### 5.4 指摘の受け渡し（再生成入力）

- **RG-09**: 再生成（T8/T11 後の 生成(g+1)）では、生成エージェントに次を渡さ**なければならない**（MUST）:
  1. 直前世代の候補JSON。
  2. 直前世代の機械検査レポートの全違反（違反ごとの箇所・計測値）。
  3. 直前世代の `review_result` の `violations[]` 全件（違反箇所・想定レベル・修正案を含む構造化指摘）。
  4. T11 経由の場合は `set_check.py` の違反レポート。
  5. 機械検査誤検出疑い報告（第7節）がある場合はそれも渡すが、「疑いがあっても機械検査違反は回避対象である」ことを再生成指示に明記する（誤検出疑い箇所を温存した再生成をしては**ならない**（MUST NOT）。当該セット内では機械検査が正である）。
- **RG-10**: 再生成に渡すのは**直前世代**の指摘のみとする。それより前の世代の指摘を累積して渡しては**ならない**（MUST NOT）。理由: 文脈肥大の防止。過去指摘の再発は新世代の機械検査・レビューが再検出する。
- **RG-11**: 再レビュー（新世代のレビュー）は毎回独立であり、前世代のレビュー結果を封筒に含めては**ならない**（MUST NOT）（RC-07）。

### 5.5 補充規則（提案モードのみ）

- **RG-12**: 提案モードでは、対象確定時に `lookup.py` が返した適格候補一覧のうち採用されなかった項目を、返却順のまま**補充プール**として保持し**なければならない**（MUST）。補充はプールの先頭から順に取り、無作為選択をしては**ならない**（MUST NOT）（決定性・監査可能性のため）。
- **RG-13**: 補充対象の問題も通常と同一のループ（世代上限3・機械検査・独立レビュー）に従う。補充に緩和された規則は存在しない。
- **RG-14**: 補充のたびに試行対象総数を1加算し、RG-03 の上限（2N）を検査する。上限到達後の不成立は S3 により教師照会へ移る。
- **RG-15**: 明示モードには自動補充が存在しない。不成立は常に教師照会（S4）である（MUST）。

### 5.6 教師照会

対話文言・画面遷移は `docs/interaction-flow.md` が正。本節はループ側の契約を定める。

- **RG-16**: 教師照会では、教師に次の情報を提示し**なければならない**（MUST）: 不成立となった対象、全世代の不合格理由サマリー（世代ごとの機械検査違反・レビュー violations の要約）、現在の確定問題数/要求数、試行対象総数/上限2N。
- **RG-17**: 提示する選択肢は次の3つに限定する（MUST）: ①代替対象の指定（試行対象総数<2N かつ未使用の `question_id` が残っている場合のみ提示。RG-19）、②当該スロットの減数、③セット中止。試行対象総数が2Nに達している場合、または未使用の `question_id` が無い場合は②③のみを提示する。
- **RG-18**: 教師が代替対象を指定した場合（明示モード・提案モードとも）、その対象は明示指定として即時に原本照合（`docs/interaction-flow.md` の明示指定照合フロー）にかけ、照合通過後に `gen1` から開始する。試行対象総数に加算する。
- **RG-19（補充・代替対象の question_id 採番）**: 補充（S2）・代替（S5）の対象には、未使用の最小の `question_id`（`q01`〜`q20` の範囲内）を新規採番し**なければならない**（MUST）。不成立となったスロットの `question_id` を再利用しては**ならない**（MUST NOT。割り当て済みIDの再割り当て禁止は `docs/json-output-spec.md` ID-02、同名監査ファイルの上書き禁止は AU-05）。不成立スロットのIDは欠番となり `set.json` に収録されない（`final_question_ids` に含めない。RG-08）。未使用の `question_id` が存在しない場合（要求数が20で全IDが割り当て済みの場合）は補充・代替を実行できないため、S2 の自動補充は行わず教師照会（S3）へ移り、照会では減数・セット中止のみを提示する（RG-17）。

### 5.7 疑似コード（規範）

## 6. インフラ障害の扱い（レビュー系）

インフラ障害とは、候補の品質と無関係な実行系の失敗である。**問題の不合格に数えず、世代を消費しない**（D-20）。

- **INF-01**: 次の事象をレビュー系インフラ障害として扱わ**なければならない**（MUST）:
  1. レビュアー出力が `review_result.schema.json` のスキーマ検証を通過しない。
  2. レビュアー出力がJSONとして構文解析できない。
  3. レビュアープロセスの起動失敗・異常終了（Claude Code の Task 失敗、`codex exec` の非ゼロ終了）。
  4. レビュアーが出力を返さない（ホストツールのタイムアウト・空出力）。
- **INF-02**: インフラ障害が発生した場合、同一世代・同一封筒でレビューを再実行する（最大2回。初回と合わせ最大3実行）。封筒の内容を変更しては**ならない**（MUST NOT）。
- **INF-03**: 3実行すべてが失敗した場合、**セットを中止**し（S8）、`E-CONTRACT-xx` 系の定義済みエラー（具体コードは `docs/architecture.md` の目録が正）と日本語の対処手順を教師に提示して停止する（MUST）。`set.json` は書かない（RG-07）。
- **INF-04**: 各失敗実行の生出力（得られた範囲のテキスト全文）とスキーマ検証エラーを監査ファイル `review/<question_id>.<gen>.review.invalid<k>.txt`（k=1,2,3）として保存し**なければならない**（MUST）（第8節）。
- **INF-05**: `review_result` が **スキーマは通過するが内容がRR-01〜RR-05の記入規則に違反する**場合（例: `verdict: fail` なのに `violations` が空、checks に欠番がある）、スキーマで機械検査可能な範囲はスキーマ側で拒否される設計とする（`schemas/review_result.schema.json` の責務）。スキーマで表現できない記入規則違反をオーケストレータが検出した場合も INF-01 と同じくインフラ障害として扱う（MUST）。
- **INF-06**: 生成側のインフラ障害のうち、candidate受理検証不通過（生成出力に起因する`E-CONTRACT-01` / `E-INPUT-03`、厳格パース失敗、JS-01正準化失敗）はD-20のとおり同一世代内1回再指示→失敗なら世代消費であり（T2/T3）、インフラ障害としては扱わない。生成エージェント自体のプロセス異常（ホストツールのセッション断）はセット中断であり、`set.json` が存在しないことで未完成が自明となる（再開機能はv2課題。`docs/requirements.md` のスコープ外リスト参照）。
- **INF-07（タイムアウト）**: オーケストレータはレビュアー1実行に `data/config/limits.json` の運用パラメータ `review_timeout_seconds`（既定300秒）のタイムアウトを適用しなければならない（MUST）。超過は INF-01 の4号（出力を返さない）としてインフラ障害に数え、INF-02 の再実行規則に従う。両アダプタはこの値を各起動機構（Taskの待機・サブプロセスの待機）に適用しなければならない（MUST。`docs/cross-agent-compatibility.md` COR-09）。

## 7. 機械検査誤検出疑いの報告様式

機械検査（spaCyによるレンマ化・POSタグ付けに依存）には誤検出があり得る。レビュアーは誤検出の疑いを構造化して報告する。**報告しても当該セットでは不合格のままであり**、機械検査側の修正は運用（`docs/architecture.md` の運用手順）で行う。

- **FP-01**: レビュアーは、機械検査レポートの違反のうち次のいずれかに該当する疑いがあるものを報告**しなければならない**（MUST。疑いを持ったのに報告しない省略は禁止）:
  1. レンマ化誤りの疑い（例: 不規則活用形が誤ったレンマに還元され辞書外扱いになった）。
  2. POSタグ付け誤りの疑い（例: 動名詞が名詞タグとなり pos 不一致違反になった）。
  3. 複数語見出しの照合漏れの疑い（トークン列マッチが先行適用されるべき表現が単語照合で違反になった）。
  4. 免除規則（数字・記号・句読点・縮約展開・固有名詞allowlist）の適用漏れの疑い。
  5. 計測誤りの疑い（語数・出現回数・字数の計測が仕様（`docs/cefrj-validation-spec.md`）と食い違う）。
- **FP-02**: 報告は `review_result` の `machine_check_disputes[]`（フィールド名・構造の正は `schemas/review_result.schema.json`）に、疑い1件につき1要素で記録する。各要素に記入し**なければならない**内容（MUST）:
  - `machine_violation_code`: 疑い対象の機械検査違反コード（機械検査レポートの `code` をそのまま引用。コード体系の正は `docs/cefrj-validation-spec.md`）
  - `location`: 疑い対象の箇所（機械検査レポートの指摘箇所の引用）
  - `dispute_type`: FP-01 の分類 1〜5 に対応する値（`lemmatization` / `pos_tagging` / `multiword_match` / `exemption` / `measurement` の5値）
  - `claim`: 誤検出と疑う理由（日本語。「正しくは〜であるはず」という形で具体的に）
  - `evidence`: 根拠（正規化データの該当エントリの引用: `lex:` ID・headword・pos、または言語学的事実の記述）
  - `suggested_correction`: 機械検査側の修正示唆（例: 「レンマ例外表に went→go を追加」「複数語見出し `check-in counter` のトークン列マッチを確認」）
- **FP-03**: 報告があっても、レビュアーは当該違反を前提とした判定を維持し**なければならない**（MUST）: 世代判定は RC-16 のとおり機械検査違反により `fail` のままである。レビュアーの `verdict` はレビュアー担当項目のみで判定し、報告の有無に影響されない。
- **FP-04**: オーケストレータは `machine_check_disputes[]` が非空の `review_result` を受領した場合、①監査に通常どおり保存し、②セット完了/中止時の完了報告（`docs/interaction-flow.md`）に「機械検査誤検出疑い n件（詳細は監査ファイル参照）」を含め**なければならない**（MUST）。教師はこれを機械検査側の修正（運用手順は `docs/architecture.md`）の起点とする。
- **FP-05**: 報告例（参考。構造の正はスキーマ）:

```json
{
  "machine_violation_code": "V-LEX-01",
  "location": "sentence token 5: \"left\"",
  "dispute_type": "lemmatization",
  "claim": "left は leave の過去形であり、レンマ leave (lex:leave:verb, A1) で照合されるべきです。形容詞 left として照合された疑いがあります。",
  "evidence": "data/normalized/lexicon.json に lex:leave:verb (A1) が存在します。文中の left は動詞過去形として機能しています。",
  "suggested_correction": "spaCy の品詞タグ付け結果を確認し、文脈上動詞の場合のレンマ照合を検証してください。"
}
```

## 8. 監査ファイル配置

監査ファイルの内容・フィールド仕様の正は `docs/json-output-spec.md`。本節はループ上の**配置・命名・書き込みタイミング**を定める。

- **AU-01**: 全監査ファイルは `output/<set_id>/review/` 直下に置く（MUST）。サブディレクトリを作っては**ならない**（MUST NOT）。
- **AU-02**: 試行単位の正規監査ファイル（§6共通定数の固定命名）:

| ファイル名 | 内容 | 書き込みタイミング |
|---|---|---|
| `review/<question_id>.<gen>.candidate.json` | candidate受理検証通過済み候補 | T1 通過直後 |

| `review/<question_id>.<gen>.review.json` | スキーマ通過済み `review_result` | T5 通過直後 |

- **AU-03**: 異常系の補助監査ファイル（本文書が命名の正）:

| ファイル名 | 内容 | 書き込みタイミング |
|---|---|---|
| `review/<question_id>.<gen>.candidate.invalid<k>.txt`（k=1,2） | candidate受理検証不通過の生成出力と診断（内容形式はAUD-09） | T2 / T3 |

- **AU-04**: 書き込みは各遷移の発生直後に行わ**なければならない**（MUST。セット完了までバッファしてはならない）。これによりセット中断時にも全試行の監査が残る。
- **AU-05**: 監査ファイルを事後に変更・削除しては**ならない**（MUST NOT）。同名ファイルが既に存在する状態での上書きはデータ整合エラー（`E-DATA-xx` 系、目録は `docs/architecture.md`）として停止する（MUST）。
- **AU-06**: `set.json` からの監査参照は相対パス（`review/` 起点）で行い、監査ファイルが欠けても `set.json` 単体で自立解釈可能でなければならない（MUST）。参照フィールドの仕様は `docs/json-output-spec.md` が正。
- **AU-07**: 世代が T3（candidate受理検証2連続不通過）で消費された場合、当該世代の `candidate.json` / `machine.json` / `request.json` / `review.json` は存在しない。監査上は `candidate.invalid1.txt` / `candidate.invalid2.txt` の存在が当該世代の試行と帰結を示す。
