## 独立検査の指摘

## R23-01 — major — `tests/unit/test_fixtures.py:1244` / `tests/unit/test_fixtures.py:1357` / `tests/unit/test_fixtures.py:1405` / `tests/unit/test_fixtures.py:3495`

1. **指摘内容**: CI-R-03のsensitive callable追跡は、dict viewをいったん名前へ束縛する形と、分岐内ローカル変数からコンテナを返す形で引き続きfail-openになる。実際に次の2反例は、実行時には`unknown_helper()`由来の値を`write_json`へ渡すが、`contract_dict_violations()`はいずれも違反ゼロを返した。

   ```python
   from tests.support import write_json
   calls = {"sink": write_json}
   view = calls.items()
   (key, fn), = view
   fn(candidate_path, unknown_helper())
   ```

   ```python
   from tests.support import write_json
   def choose(flag):
       if flag:
           calls = (write_json,)
       else:
           calls = (write_json,)
       return calls
   choose(True)[0](candidate_path, unknown_helper())
   ```

   `static_callable_container()`が名前へ保存できるdict viewは`values()`だけで、`items()`は保存しない。一方、`unresolved_binding_terminal()`は`items`・`keys`・`values`を未知抽出のfail-closed対象から除外するため、`view`への束縛時にsensitive identityが消える。また、`returned_callable_container()`は関数本体のトップレベルにある`Assign` / `AnnAssign`だけを順に解析し、`If`等の分岐内代入を合流しないため、`return calls`を解決できない。この2経路により、第4節fixtureでも製品直前段出力でもない入力をJSON書込みsinkへ渡す将来のテストをマージゲートが検出できない。

2. **根拠となる設計文書の規則ID**: `docs/testing-and-acceptance.md` CI-R-03・TST-08、`IMPLEMENTATION_PLAN.md` M8 DoD 1。

3. **具体的な修正案**: `keys()` / `values()` / `items()`のview種別と要素対応を名前への代入後も保持し、アンパック・反復・ネスト抽出へ伝播する。構造を静的に確定できないsensitive viewは、各束縛先を`unresolved-sensitive`としてfail-closedにする。関数戻り値については`If` / `Try` / `Match` / loopのローカルcontainer状態を分岐ごとに解析・合流し、全分岐が同じsensitiveコンテナならそのidentityを返し、合流不能ならsensitive戻り値として拒否する。上記2反例と、同形で正準fixture由来データだけを渡す正常例を自己回帰へ追加する。

## R23-02 — major — `.claude/settings.json:5` / `.claude/settings.json:100` / `.claude/hooks/guard_staging.py:147` / `tests/unit/test_flow_control.py:143`

1. **指摘内容**: Claude Codeホストは`Read`以外の読み取り系ツール`Grep`を使ってC12専用`.staging/flow-state.json`の内容を取得できる。権限設定は`Read(./**)`でリポジトリ全体の読取りを許可し、専用PreToolUse matcherは`Read|Write|Edit`だけである。ガード本体も`tool_name == "Read"`だけを`guard_read()`へ送り、`Grep`を検査しない。そのため、例えば`pattern="generation"`、`path="output/<set_id>/.staging/flow-state.json"`の`Grep`イベントはガードを終了コード0で通過する。`Grep`は指定ファイルまたは祖先ディレクトリを検索して一致内容を返せるため、ホストは公開経路`flow_control.py status`を経由せず、世代・再試行・現在candidate/machine・採用済みスロット等の内部stateを観測できる。追加された回帰も`tool_name="Read"`だけを検査しており、この経路を検出しない。

2. **根拠となる設計文書の規則ID**: `docs/cross-agent-compatibility.md` CCW-11、`DECISIONS.md` M8D-09。

3. **具体的な修正案**: `flow-state.json`を対象にした`Read` deny規則を、Claude Codeの全組込み読取り系ツールへ適用される形で追加するか、少なくとも`Grep`をPreToolUse matcherとガードへ追加する。`Grep`はファイル直接指定だけでなく`.staging`、対象set-dir、`output/`、リポジトリルート等の祖先を検索範囲にできるため、検索範囲に内部stateが含まれる場合も拒否または当該ファイルを確実に除外する。`Read`と`Grep`の相対・絶対・祖先ディレクトリ指定が内部stateを取得できず、通常の仕様・監査ファイル検索は維持されることをCLI回帰へ追加する。
